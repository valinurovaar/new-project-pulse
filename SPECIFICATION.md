# Техническое задание: ProjectPulse

## 1. Назначение системы

**ProjectPulse** — HTTP API для мониторинга технического состояния пользовательских веб-проектов.

Система позволяет зарегистрированному пользователю добавлять веб-проекты, запускать проверки их доступности и получать информацию о найденных проблемах.

Базовые проверки выполняются бесплатно. За стабильную работу проектов пользователю начисляются диагностические кредиты. Кредиты можно расходовать на расширенные проверки производительности, безопасности и конфигурации проекта.

## 2. Основные требования к бизнес-логике

Система должна поддерживать:

- регистрацию, аутентификацию и авторизацию пользователей;
- добавление и хранение веб-проектов пользователя;
- автоматическую и ручную проверку состояния проектов;
- взаимодействие с внешней системой диагностики;
- хранение истории проверок;
- расчёт текущего состояния проекта;
- начисление диагностических кредитов за стабильную работу;
- списание кредитов за расширенные проверки;
- ведение журнала начислений и списаний.

## 3. Сценарий взаимодействия

1. Пользователь регистрируется в ProjectPulse.
2. Пользователь добавляет URL своего веб-проекта.
3. Система сохраняет проект и создаёт задачу на базовую проверку.
4. Фоновый обработчик передаёт задачу внешней системе диагностики.
5. Внешняя система проверяет доступность и состояние проекта.
6. ProjectPulse периодически запрашивает результат диагностики.
7. После завершения проверки система сохраняет результат и обновляет состояние проекта.
8. Если проект признан исправным, пользователь получает диагностические кредиты.
9. Пользователь может потратить кредиты на расширенную проверку.
10. Результаты всех проверок сохраняются в истории.

## 4. Основные сущности

### Пользователь

Содержит:

- уникальный идентификатор;
- логин;
- хеш пароля;
- дату регистрации;
- баланс диагностических кредитов.

### Проект

Содержит:

- уникальный идентификатор;
- идентификатор владельца;
- название;
- URL;
- текущее состояние;
- оценку надёжности;
- дату добавления;
- дату последней проверки.

### Проверка

Содержит:

- уникальный идентификатор;
- идентификатор проекта;
- тип проверки;
- статус выполнения;
- идентификатор задачи во внешней системе;
- результат;
- время создания, запуска и завершения.

### Операция с кредитами

Содержит:

- уникальный идентификатор;
- идентификатор пользователя;
- тип операции;
- количество кредитов;
- баланс после операции;
- основание начисления или списания;
- дату выполнения.

## 5. Состояния проекта

Проект может иметь одно из следующих состояний:

- `UNKNOWN` — проект ещё не проверялся;
- `HEALTHY` — проект работает нормально;
- `DEGRADED` — проект доступен, но обнаружены проблемы;
- `CRITICAL` — проект недоступен или обнаружены критические ошибки;
- `ARCHIVED` — проект перемещён пользователем в архив.

Внешний сервис возвращает оценку проекта от `0` до `100`.

ProjectPulse определяет состояние проекта следующим образом:

| Оценка | Состояние |
|---:|---|
| 80–100 | `HEALTHY` |
| 50–79 | `DEGRADED` |
| 0–49 | `CRITICAL` |

Если внешняя система не смогла выполнить проверку по технической причине, состояние проекта изменяться не должно.

## 6. Типы проверок

### BASIC

Бесплатная базовая проверка:

- доступность проекта;
- HTTP-код ответа;
- время ответа;
- наличие HTTPS;
- срок действия TLS-сертификата.

### PERFORMANCE

Расширенная проверка производительности. Стоимость — **10 кредитов**.

### SECURITY

Проверка базовых настроек безопасности. Стоимость — **20 кредитов**.

### CONFIGURATION

Проверка HTTP-заголовков, перенаправлений, TLS и общедоступной конфигурации. Стоимость — **15 кредитов**.

Типы расширенных проверок не должны подразумевать эксплуатацию уязвимостей или атаки на проверяемый проект.

## 7. Статусы проверки

Проверка может иметь один из следующих статусов:

- `NEW` — создана в ProjectPulse;
- `QUEUED` — передана внешнему сервису;
- `RUNNING` — выполняется;
- `COMPLETED` — успешно завершена;
- `FAILED` — не выполнена из-за технической ошибки;
- `CANCELLED` — отменена системой.

Статусы `COMPLETED`, `FAILED` и `CANCELLED` являются окончательными.

## 8. Правила начисления кредитов

После регистрации пользователь получает **30 стартовых кредитов**.

За успешную базовую проверку проекта в состоянии `HEALTHY` начисляется **5 кредитов**.

Ограничения:

- за один проект кредиты начисляются не чаще одного раза в сутки;
- пользователь может получить за стабильность проектов не более 20 кредитов в сутки;
- ручной повторный запуск проверки не позволяет обойти ограничения;
- за расширенные проверки кредиты не начисляются;
- за проекты со статусом `DEGRADED` или `CRITICAL` кредиты не начисляются.

Все изменения баланса должны выполняться транзакционно.

Баланс пользователя не может становиться отрицательным.

## 9. Сводное HTTP API

Сервис должен предоставлять следующие обработчики:

```text
POST   /api/v1/users/register
POST   /api/v1/users/login

POST   /api/v1/projects
GET    /api/v1/projects
GET    /api/v1/projects/{project_id}
DELETE /api/v1/projects/{project_id}

POST   /api/v1/projects/{project_id}/checks
GET    /api/v1/projects/{project_id}/checks

POST   /api/v1/projects/{project_id}/audits
GET    /api/v1/audits

GET    /api/v1/balance
GET    /api/v1/transactions
```

## 10. Регистрация пользователя

### Обработчик

```http
POST /api/v1/users/register
Content-Type: application/json
```

### Тело запроса

```json
{
  "login": "developer",
  "password": "strong-password"
}
```

Логин должен быть уникальным.

После успешной регистрации пользователь автоматически считается аутентифицированным.

### Коды ответа

- `200` — пользователь зарегистрирован;
- `400` — неверный формат запроса;
- `409` — логин уже занят;
- `500` — внутренняя ошибка.

### Пример ответа

```json
{
  "token": "<access-token>"
}
```

## 11. Аутентификация

### Обработчик

```http
POST /api/v1/users/login
Content-Type: application/json
```

### Тело запроса

```json
{
  "login": "developer",
  "password": "strong-password"
}
```

### Коды ответа

- `200` — пользователь аутентифицирован;
- `400` — неверный формат запроса;
- `401` — неверный логин или пароль;
- `500` — внутренняя ошибка.

Для последующих запросов рекомендуется использовать заголовок:

```http
Authorization: Bearer <access-token>
```

## 12. Добавление проекта

### Обработчик

```http
POST /api/v1/projects
Authorization: Bearer <access-token>
Content-Type: application/json
```

### Тело запроса

```json
{
  "name": "My Portfolio",
  "url": "https://example.com"
}
```

После добавления проекта система автоматически создаёт базовую проверку.

### Ограничения

- разрешены только схемы `http` и `https`;
- длина URL не должна превышать 2048 символов;
- URL не должен содержать логин и пароль;
- пользователь не может дважды добавить одинаковый нормализованный URL;
- имя проекта обязательно и не должно превышать 100 символов;
- запрещается проверка локальных и служебных адресов.

К запрещённым адресам относятся:

- `localhost`;
- loopback-адреса;
- link-local-адреса;
- приватные IP-диапазоны;
- адреса внутренних сетевых сервисов.

### Коды ответа

- `201` — проект создан;
- `400` — некорректный JSON;
- `401` — пользователь не авторизован;
- `409` — проект с таким URL уже добавлен пользователем;
- `422` — некорректный или запрещённый URL;
- `500` — внутренняя ошибка.

### Пример ответа

```json
{
  "id": "978b7809-1ae8-4f85-a0a9-847d76de74ae",
  "name": "My Portfolio",
  "url": "https://example.com",
  "status": "UNKNOWN",
  "score": null,
  "created_at": "2026-09-29T14:20:00+03:00"
}
```

При отсутствии проектов возвращается пустой массив.

## 14. Получение проекта

### Обработчик

```http
GET /api/v1/projects/{project_id}
Authorization: Bearer <access-token>
```

Пользователь может получить информацию только о собственном проекте.

### Коды ответа

- `200` — проект найден;
- `400` — некорректный идентификатор;
- `401` — пользователь не авторизован;
- `403` — проект принадлежит другому пользователю;
- `404` — проект не найден;
- `500` — внутренняя ошибка.

## 15. Архивация проекта

### Обработчик

```http
DELETE /api/v1/projects/{project_id}
Authorization: Bearer <access-token>
```

Проект не удаляется физически. Он получает состояние `ARCHIVED`.

Новые автоматические проверки для него больше не создаются. История проверок и операций сохраняется.

### Коды ответа

- `204` — проект перемещён в архив;
- `400` — некорректный идентификатор;
- `401` — пользователь не авторизован;
- `403` — проект принадлежит другому пользователю;
- `404` — проект не найден;
- `409` — у проекта выполняется проверка;
- `500` — внутренняя ошибка.

## 16. Запуск базовой проверки

### Обработчик

```http
POST /api/v1/projects/{project_id}/checks
Authorization: Bearer <access-token>
```

Базовая проверка бесплатна.

Одновременно у проекта может выполняться только одна базовая проверка.

Если активная проверка уже существует, новая не создаётся, а сервис возвращает информацию о текущей проверке.

### Коды ответа

- `202` — новая проверка принята;
- `200` — проверка уже выполняется;
- `401` — пользователь не авторизован;
- `403` — проект принадлежит другому пользователю;
- `404` — проект не найден;
- `409` — проект находится в архиве;
- `500` — внутренняя ошибка.

### Пример ответа

```json
{
  "id": "3a8aff96-9021-43e8-850c-ef03744b120f",
  "project_id": "978b7809-1ae8-4f85-a0a9-847d76de74ae",
  "type": "BASIC",
  "status": "NEW",
  "created_at": "2026-09-29T15:00:00+03:00"
}
```

### Обработчик

```http
GET /api/v1/projects/{project_id}/checks
Authorization: Bearer <access-token>
```

Проверки сортируются по времени создания от новых к старым.

### Пример ответа

```json
[
  {
    "id": "3a8aff96-9021-43e8-850c-ef03744b120f",
    "type": "BASIC",
    "status": "COMPLETED",

    "created_at": "2026-09-29T15:00:00+03:00",
    "completed_at": "2026-09-29T15:00:08+03:00"
  }

```

### Коды ответа

- `200` — история получена;
- `401` — пользователь не авторизован;
- `403` — проект принадлежит другому пользователю;
- `404` — проект не найден;
- `500` — внутренняя ошибка.

## 18. Запуск расширенной проверки

### Обработчик

```http
POST /api/v1/projects/{project_id}/audits
Authorization: Bearer <access-token>
Content-Type: application/json
```

### Тело запроса

```json
{
  "type": "SECURITY"
}
```

Допустимые типы:

- `PERFORMANCE`;
- `SECURITY`;
- `CONFIGURATION`.

При создании проверки необходимое количество кредитов списывается атомарно.

Если передать запрос повторно при уже выполняющейся проверке того же типа, новая проверка не создаётся.

### Правила возврата кредитов

Кредиты возвращаются, если:

- внешний сервис недоступен;
- задача не была принята внешним сервисом;
- проверка завершилась внутренней технической ошибкой;
- задача была отменена системой.

Кредиты не возвращаются, если проверка успешно завершилась и обнаружила проблемы.

### Коды ответа

- `202` — проверка создана, кредиты списаны;
- `400` — неверный формат запроса;
- `401` — пользователь не авторизован;
- `402` — недостаточно кредитов;
- `403` — проект принадлежит другому пользователю;
- `404` — проект не найден;
- `409` — аналогичная проверка уже выполняется или проект архивирован;
- `422` — неизвестный тип проверки;
- `500` — внутренняя ошибка.

# Внешняя система диагностики

Внешняя система представляет собой отдельный доверенный сервис. Её внутренняя реализация не входит в ProjectPulse.

ProjectPulse взаимодействует с ней асинхронно.

## 22. Создание диагностической задачи

```http
POST /api/v1/inspections
Content-Type: application/json
```

### Запрос

```json
{
  "target": "https://example.com",
  "type": "BASIC"
}
```

### Успешный ответ

```http
202 Accepted
```

```json
{
  "task_id": "external-task-123",
  "status": "QUEUED"
}
```

### Возможные ответы

- `202` — задача принята;
- `400` — неверный запрос;
- `422` — адрес невозможно проверить;
- `429` — превышен лимит запросов;
- `500` — внутренняя ошибка внешнего сервиса;
- `503` — сервис временно недоступен.

При ответе `429` внешний сервис передаёт заголовок:

```http
Retry-After: 60
```

## 23. Получение результата диагностики

```http
GET /api/v1/inspections/{task_id}
```

### Незавершённая проверка

```json
{
  "task_id": "external-task-123",
  "status": "RUNNING"
}
```

### Завершённая проверка

```json
{
  "task_id": "external-task-123",
  "status": "COMPLETED",
  "score": 92,
  "result": {
    "available": true,
    "status_code": 200,
    "response_time_ms": 184,
    "https": true,
    "certificate_expires_at": "2026-12-20T00:00:00Z",
    "issues": []
  }
}
```

### Проверка с найденными проблемами

```json
{
  "task_id": "external-task-456",
  "status": "COMPLETED",
  "score": 63,
  "result": {
    "available": true,
    "status_code": 200,
    "response_time_ms": 2150,
    "https": true,
    "issues": [
      {
        "code": "SLOW_RESPONSE",
        "severity": "WARNING",
        "message": "Server response time exceeds 2000 ms"
      }
    ]
  }
}
```

### Статусы внешней задачи

- `QUEUED`;
- `RUNNING`;
- `COMPLETED`;
- `FAILED`.

## 24. Фоновая обработка

ProjectPulse должен содержать фоновые обработчики, которые:

- передают новые проверки внешней системе;
- опрашивают состояние незавершённых задач;
- учитывают `Retry-After`;
- повторяют запросы после временных ошибок;
- сохраняют результаты;
- обновляют состояние проекта;
- начисляют кредиты;
- возвращают кредиты при техническом провале расширенной проверки;
- создают периодические базовые проверки.

Повторная обработка одной задачи не должна приводить к повторному начислению или возврату кредитов.

После перезапуска приложения обработка незавершённых задач должна продолжаться.

## 25. Автоматические проверки

Система должна периодически создавать базовые проверки активных проектов.

По умолчанию интервал составляет 24 часа.

Новая автоматическая проверка не создаётся, если:

- проект архивирован;
- у проекта уже есть активная базовая проверка;
- с последней проверки прошло меньше настроенного интервала.

## 26. Общие ограничения

- хранилище данных — PostgreSQL;
- идентификаторы основных сущностей — UUID;
- даты передаются в формате RFC3339;
- пароли должны храниться только в виде криптографического хеша;
- кредиты хранятся как целые числа;
- баланс изменяется только внутри транзакции;
- пользователь не должен получать доступ к проектам другого пользователя;
- повторная обработка результата внешней проверки должна быть идемпотентной;
- сервис должен корректно завершать работу при получении сигнала остановки;
- HTTP-клиент внешнего сервиса должен иметь тайм-ауты;
- API должно возвращать `Content-Type: application/json` для JSON-ответов;
- ошибки должны возвращаться в едином формате.

### Формат ошибки

```json
{
  "error": {
    "code": "INSUFFICIENT_CREDITS",
    "message": "Not enough diagnostic credits"
  }
}
```

## 27. Конфигурирование

Сервис должен поддерживать переменные окружения и флаги командной строки:

| Назначение | Переменная | Флаг |
|---|---|---|
| Адрес запуска | `RUN_ADDRESS` | `-a` |
| Подключение к PostgreSQL | `DATABASE_URI` | `-d` |
| Адрес диагностического сервиса | `INSPECTOR_ADDRESS` | `-i` |
| Секрет подписи токенов | `AUTH_SECRET` | `-s` |
| Интервал автоматических проверок | `CHECK_INTERVAL` | `-c` |
| Число фоновых обработчиков | `WORKER_COUNT` | `-w` |

Значения переменных окружения имеют приоритет над значениями флагов.

## 28. Тестирование и документация

Обязательные требования:

- покрытие бизнес-логики модульными тестами не менее 60%;
- тестирование HTTP-обработчиков;
- тестирование начисления и списания кредитов;
- тестирование защиты от повторного начисления;
- тестирование переходов между статусами;
- документация для экспортируемых функций, типов и пакетов;
- миграции базы данных;
- инструкция по запуску проекта.
